1. 아키텍처 결정사안

에이전틱 AI 코딩 도구를 사내에 배포할 때, 코드 실행 위치와 네트워크 접근 범위가 보안·품질·운영 전반에 영향을 미치는 최상위 설계 결정이다. 아래 3가지 아키텍처 안을 비교한다.

안 A — 에어갭 서버 실행

에이전틱 AI 도구를 사내 서버(K3s 클러스터)에서 실행하며, 인터넷 연결을 완전히 차단하는 구조. 모든 LLM 추론, 코드 실행, 파일 접근이 사내 네트워크 안에서만 이루어진다.

개발자 PC (브라우저) Windows / 사내망
↓ HTTPS
사내 서버 (에어갭)
Ingress / 인증 게이트웨이 Traefik + AD/SSO 인증
↓
사용자별 격리 Pod • 에이전틱 코딩 도구
• 터미널 (ttyd)
• 워크스페이스 (PVC)
↔
사내 LLM (vLLM) • Qwen / DeepSeek 등
• 사내 GPU 클러스터
사내 GitLab
사내 Registry
사내 문서 DB
↓
✕
인터넷 완전 차단

장점

  • 보안 최상: 사내 코드·정보가 물리적으로 외부에 노출될 수 없음. 보안팀 승인 획득이 가장 용이
  • 규정 준수 용이: 사내 정보보호 정책, 개인정보보호법 등 컴플라이언스 이슈 없음
  • 네트워크 구성 단순: 프록시, 필터링 인프라 불필요. 방화벽 규칙이 단순
  • 예측 가능한 비용: 외부 API 호출 비용 없음. GPU 인프라 비용만 관리
  • 사내 시스템 완전 통합: GitLab, Jenkins, 사내 DB 등과 지연 없이 연동 가능

단점

  • LLM 품질 한계: 사내 LLM(Qwen 3.5 등)은 SotA 모델(Claude Opus, GPT-5) 대비 추론·문서 작성 능력에 상당한 격차 존재
  • 웹 검색 불가: 최신 라이브러리 문서, Stack Overflow, API 레퍼런스 등 실시간 참조 불가. 에이전트의 문제 해결 능력 제한
  • 패키지 설치 제약: npm, pip 등 외부 패키지 레지스트리 접근 불가. 사내 미러 구축·유지 필요
  • 에이전트 도구 제한: WebSearch, WebFetch 등 인터넷 의존 도구 사용 불가. 에이전트 활용 시나리오 축소
  • 모델 업데이트 지연: 새 모델 도입 시 수동 다운로드·배포 필요. 에어갭 환경의 운영 오버헤드

리스크

  • 품질 기대치 미충족 (높음): 팀장 기대인 "Cowork 수준 문서 품질"을 사내 LLM만으로 달성하기 어려움. PoC 결과가 기대 이하일 경우 프로젝트 방향 재검토 필요
  • 개발자 채택률 저하 (중간): 외부 정보 참조 불가로 인해 기존 웹 검색 + ChatGPT 조합 대비 체감 가치가 낮을 수 있음
  • 사내 미러 운영 부담 (중간): npm, PyPI, Docker Hub 등의 사내 미러 구축·동기화 필요. 미러 관리 인력 소요
  • 기술 부채 누적 (낮음): 에어갭 특화 워크어라운드(오프라인 빌드, 수동 패치 등)가 장기적으로 유지보수 부담 발생

안 B — 서버 실행 + 도메인 화이트리스트

에이전틱 AI 도구를 사내 서버에서 실행하되, 프록시를 통해 허용된 도메인에만 인터넷 접근을 허용하는 구조. Claude Cowork 데스크톱의 보안 모델(gVisor + MITM 프록시 + 도메인 허용목록)과 동일한 접근 방식이다.

개발자 PC (브라우저) Windows / 사내망
↓ HTTPS
사내 서버 (제어된 네트워크)
Ingress / 인증 게이트웨이 Traefik + AD/SSO 인증
↓
사용자별 격리 Pod • 에이전틱 코딩 도구
• 터미널 (ttyd)
• 워크스페이스 (PVC)
↔
사내 LLM (vLLM) • Qwen / DeepSeek 등
• 사내 GPU 클러스터
↓
이그레스 프록시 (Squid/Envoy) • 도메인 화이트리스트 적용
• TLS 검사 (MITM 프록시)
• 요청 로깅 및 감사
• 사내 정보 포함 요청 차단 규칙
↓
허용 도메인만 통과
docs.python.org 기술 문서
registry.npmjs.org 패키지 레지스트리
stackoverflow.com 기술 Q&A
기타 ... 허용 목록 관리

장점

  • 품질 향상: 에이전트가 공식 문서, Stack Overflow 등 참조 가능. 최신 API 문서 기반 코드 생성 품질 개선
  • Cowork 동일 보안 모델: Anthropic이 Cowork에서 검증한 보안 패턴(도메인 화이트리스트)을 그대로 적용. 업계 검증된 접근법
  • 패키지 관리 용이: npm, pip 등 공식 레지스트리에 직접 접근 가능. 사내 미러 불필요
  • 보안 통제 유지: 코드 실행은 여전히 서버 Pod 내부. 사내 정보가 개발자 PC를 거치지 않음
  • 점진적 확장: 초기에는 소수 도메인만 허용하고, 안전성 확인 후 점진적으로 확대 가능

단점

  • 프록시 인프라 구축 필요: 이그레스 프록시, TLS 검사, 도메인 관리 시스템 등 추가 인프라 구축·운영 부담
  • 화이트리스트 관리 비용: 허용 도메인 목록의 지속적 검토·갱신 필요. 관리 주체와 프로세스 정의 필요
  • 보안팀 협의 필요: "서버에서 인터넷 접근" 자체가 보안 정책 예외 승인 필요. 설득 비용 발생
  • TLS 검사 복잡성: MITM 프록시의 인증서 관리, 인증서 피닝 사이트 대응 등 운영 복잡도 증가
  • LLM 품질 한계 잔존: 인터넷 접근이 가능해져도 LLM 자체 성능은 여전히 사내 모델 수준

리스크

  • 사내 정보 유출 경로 생성 (높음): 에이전트가 웹 검색 시 프롬프트에 사내 코드/정보를 포함하여 외부로 전송할 가능성. DLP(Data Loss Prevention) 규칙 설계 필수
  • 보안 승인 지연 (중간): 보안팀의 예외 승인 절차가 길어질 경우 PoC 일정 지연. 사전 보안팀 협의 권장
  • 화이트리스트 우회 (낮음): 허용된 도메인을 통한 우회 접근(예: GitHub Gist에 정보 업로드) 가능성. 아웃바운드 콘텐츠 검사 필요
  • 프록시 장애 시 서비스 영향 (중간): 이그레스 프록시 다운 시 에이전트의 외부 참조 기능 전체 중단. HA 구성 필요

안 C — 클라이언트 직접 실행

에이전틱 AI 도구를 개발자 PC(Windows)에서 직접 실행하는 구조. LLM 추론은 사내 서버의 vLLM API를 호출하지만, 코드 실행과 파일 접근은 개발자 로컬 환경에서 이루어진다.

개발자 PC (Windows)
에이전틱 코딩 도구 (CLI/IDE 확장) • 로컬 파일 시스템 직접 접근
• 터미널 명령어 직접 실행
• IDE 통합 (VS Code 등)
로컬 프로젝트
로컬 터미널
IDE
↓ API 호출
사내 LLM (vLLM) 사내 GPU 클러스터
↓ 사내 프록시 경유
인터넷 • 기존 사내 프록시 정책 적용
• DLP 모니터링 대상
• 보안 위규 감지 가능

장점

  • 인프라 부담 최소: 서버 Pod, K3s 클러스터 등 추가 인프라 불필요. vLLM 서버만 운영
  • 개발자 경험 최상: 로컬 파일 시스템과 IDE에 직접 통합. 기존 개발 워크플로우 변경 최소
  • 빠른 PoC: 기존 오픈소스 도구(Crush, Aider 등)를 설치만 하면 즉시 사용 가능. 서버 인프라 구축 없이 평가 가능
  • 유연한 도구 선택: 개발자가 선호하는 도구(CLI, VS Code 확장 등)를 자유롭게 선택 가능

단점

  • 보안 통제 어려움: 에이전트가 로컬에서 실행하는 터미널 명령어(curl, wget 등)로 사내 정보 유출 가능. 기존 DLP로 완전 통제 어려움
  • 네트워크 명령어 리스크: 에이전트가 자율적으로 네트워크 관련 명령어 실행 시 보안 위규 발생 가능
  • 웹 검색 도구 사용 시 정보 유출: 에이전트가 사내 코드 맥락을 포함하여 외부 검색 수행 시 보안 정책 위반
  • 환경 파편화: 개발자마다 다른 OS, 도구 버전, 설정. 일관된 경험 보장 어려움
  • 관리·모니터링 불가: 개별 PC에서의 에이전트 사용 현황, 보안 이벤트 중앙 모니터링 어려움

리스크

  • 보안 위규 발생 (매우 높음): 에이전트가 자율적으로 실행하는 명령어가 사내 보안 정책(프록시 우회, 외부 데이터 전송 등)을 위반할 가능성이 높음. 사후 감사에서 문제 발견 시 전사적 이슈화
  • 보안팀 승인 거부 (높음): 개발자 PC에서 AI가 자율적으로 명령어를 실행하는 구조 자체를 보안팀이 허용하지 않을 가능성이 높음
  • 사고 책임 소재 불명확 (중간): 에이전트가 실행한 명령어로 인한 보안 사고 발생 시 개발자/AI팀/보안팀 간 책임 소재 분쟁
  • Shadow IT화 (중간): 공식 도입 전이라도 개발자들이 개별적으로 사용할 가능성. 통제 없는 사용이 보안 사고로 이어질 수 있음

3안 비교 요약

평가 항목 안 A: 에어갭 서버 안 B: 서버 + 화이트리스트 안 C: 클라이언트 실행
보안 수준 최상 상 (통제된 접근) 하 (통제 어려움)
보안팀 승인 난이도 낮음 중간 (예외 승인 필요) 높음 (거부 가능성)
에이전트 출력 품질 사내 LLM 수준 사내 LLM + 외부 참조 사내 LLM + 외부 참조
웹 검색·외부 참조 불가 허용 도메인만 기존 프록시 경유
인프라 구축 비용 높음 (K3s + 미러) 매우 높음 (K3s + 프록시) 낮음 (vLLM만)
운영 복잡도 중간 높음 (프록시 + 화이트리스트) 낮음
개발자 경험 중간 (웹 터미널) 중간 (웹 터미널) 최상 (로컬 IDE)
Cowork 모델과의 유사도 낮음 높음 (동일 보안 패턴) 없음
PoC 적합성 적합 (빠른 검증) 보통 (프록시 구축 선행) 매우 적합 (즉시 가능)
시사점: 안 B(서버 + 화이트리스트)가 Cowork의 검증된 보안 모델을 재현하면서도 외부 참조를 통한 품질 향상이 가능한 균형점이다. 단, PoC 단계에서는 인프라 구축 부담이 있으므로, 안 A로 기본 기능을 먼저 검증한 후 안 B로 확장하는 단계적 접근을 권장한다. 안 C는 보안 리스크가 높아 공식 도입보다는 개인 평가/비교 용도로만 활용하는 것이 적절하다.

2. LLM 품질 비교 테스트 시나리오

사내 LLM 사용이 확정된 상황에서, SotA 모델 대비 품질 격차를 객관적으로 측정하기 위한 테스트 시나리오를 설계한다. 테스트 결과는 향후 LLM 업그레이드, 하네스 최적화, RAG 도입 등의 투자 결정 근거로 활용된다.

테스트 매트릭스 설계

3개의 축으로 조합되는 테스트 매트릭스:

축 변수 설명
축 1: LLM 사내 LLM Qwen 3.5 (또는 사내 운영 모델) — vLLM 서빙
SotA 모델 Claude Opus 4.6 / GPT-5 — 외부 API 호출 (테스트 환경에서만 사용)
축 2: 인터넷 에어갭 인터넷 완전 차단. WebSearch/WebFetch 도구 비활성화
화이트리스트 기술 문서 사이트만 허용 (docs.python.org, MDN, npmjs.com 등)
풀 인터넷 제한 없이 모든 웹사이트 접근 가능
축 3: 작업 유형 T1. 코드 생성 주어진 요구사항으로 코드 작성
T2. 기술 문서 작성 설계 문서, API 문서 등 기술 문서 생성
T3. 자료 검색 기반 작성 외부 자료를 검색·종합하여 문서 작성
T4. 주어진 자료 기반 작성 제공된 자료(코드, 문서)만으로 분석·문서 작성
T5. 코드 리뷰/분석 기존 코드의 리뷰, 버그 분석, 리팩토링 제안
SotA 모델 테스트 시 보안 주의: 외부 API 호출 시 사내 실제 코드/정보를 사용하면 보안 위규. 테스트 전용 더미 프로젝트를 별도 준비하거나, 오픈소스 프로젝트를 테스트 대상으로 사용해야 한다.

시나리오 상세

시나리오 S1: 코드 생성 — 에어갭 환경 비교

사내 LLM SotA 모델 에어갭
테스트 목적인터넷 없이 순수 LLM 코드 생성 능력 비교. 모델 자체 성능 격차 측정의 기준선(baseline) 확보
입력 조건 프롬프트: "REST API 서버를 Go로 작성하라. JWT 인증, CRUD 엔드포인트, PostgreSQL 연동, 에러 핸들링, 테스트 코드 포함."
참고자료: 없음 (LLM 내재 지식만 사용)
인터넷: 완전 차단. WebSearch/WebFetch 비활성화
평가 기준
  • 정확성 (30%): 컴파일 가능 여부, 런타임 에러 없이 실행 여부, API 정상 동작 여부
  • 완성도 (25%): 요구사항 항목별 충족률 (JWT, CRUD, DB, 에러 핸들링, 테스트 각각 체크)
  • 코드 품질 (25%): 관용적(idiomatic) Go 코드, 적절한 패키지 구조, 에러 처리 패턴
  • 보안 (20%): SQL 인젝션 방어, JWT 시크릿 관리, 입력 검증
예상 결과SotA 모델이 정확성과 코드 관용성에서 우위. 사내 LLM은 기본 구조는 생성하나 세부 에러 처리, 테스트 완성도에서 격차 예상

시나리오 S2: 코드 생성 — 인터넷 접근에 따른 품질 변화

SotA 모델 에어갭 화이트리스트 풀 인터넷
테스트 목적동일 모델에서 인터넷 접근 범위에 따른 코드 품질 차이 측정. 화이트리스트 투자 가치 판단 근거
입력 조건 프롬프트: "최신 Pydantic v2 + FastAPI로 파일 업로드 API를 작성하라. S3 호환 스토리지 연동, 비동기 처리, OpenAPI 스키마 자동 생성."
핵심: "최신 Pydantic v2" — LLM 학습 데이터 이후 변경된 API를 정확히 사용하는지 확인
3회 실행: (a) 에어갭, (b) 화이트리스트(docs.pydantic.dev, fastapi.tiangolo.com 허용), (c) 풀 인터넷
평가 기준
  • API 최신성 (40%): Pydantic v2 문법(model_validator, ConfigDict 등) 사용 여부. v1 구문(validator, class Config) 사용 시 감점
  • 정확성 (30%): 실행 가능하고 기능이 동작하는 코드
  • 완성도 (30%): 요구 기능 전체 구현 여부
예상 결과에어갭 시 v1 구문 혼용 가능성 높음. 화이트리스트로 공식 문서 접근 시 v2 정확도 크게 향상. 풀 인터넷은 화이트리스트 대비 소폭 향상

시나리오 S3: 기술 문서 작성 — 사내 LLM vs SotA

사내 LLM SotA 모델 에어갭
테스트 목적팀장 핵심 관심사인 문서 생성 품질의 모델 간 격차 측정. 에어갭 환경에서 모델 자체의 문서 작성 능력 비교
입력 조건 프롬프트: "아래 Go 코드베이스를 분석하여 소프트웨어 설계 문서(SDD)를 작성하라. 포함 항목: 시스템 개요, 아키텍처 다이어그램(텍스트), 컴포넌트 상세, 데이터 흐름, API 명세, 에러 처리 전략, 보안 고려사항."
참고자료: 테스트용 Go 프로젝트 소스코드 (약 3,000 LoC)
인터넷: 완전 차단
평가 기준
  • 구조적 완성도 (25%): SDD 표준 항목 충족률, 논리적 흐름
  • 기술적 정확성 (25%): 코드와 문서 내용의 일치도, 아키텍처 설명 정확성
  • 깊이 (20%): 피상적 설명 vs 구현 세부사항까지 다루는 깊이
  • 가독성 (15%): 문서 구조, 용어 일관성, 문장 품질
  • 실용성 (15%): 다른 개발자가 이 문서만으로 시스템을 이해하고 수정할 수 있는 수준
예상 결과SotA 모델이 구조적 완성도, 깊이, 가독성에서 현저히 우위. 사내 LLM은 기본 구조는 생성하나 피상적 설명에 그칠 가능성. 이 시나리오의 격차가 가장 클 것으로 예상

시나리오 S4: 자료 검색 기반 문서 작성 — 인터넷 유무 영향

SotA 모델 에어갭 화이트리스트 풀 인터넷
테스트 목적에이전트에게 자료 검색부터 위임했을 때 인터넷 접근 범위에 따른 결과물 품질 차이 측정
입력 조건 프롬프트: "Kubernetes 환경에서 vLLM을 프로덕션 배포하기 위한 운영 가이드를 작성하라. GPU 스케줄링, 오토스케일링, 모니터링, 장애 대응, 보안 설정을 포함."
참고자료: 없음 (에이전트가 스스로 자료를 검색·수집해야 함)
3회 실행: (a) 에어갭 — 내재 지식만, (b) 화이트리스트 — docs.vllm.ai, kubernetes.io 허용, (c) 풀 인터넷
평가 기준
  • 정보 정확성 (30%): 설정값, 명령어, API 호출 등이 실제 동작하는 정확한 정보인지
  • 정보 최신성 (25%): 최신 버전의 vLLM/K8s 기능 반영 여부
  • 포괄성 (25%): 프로덕션 운영에 필요한 항목의 누락 없이 다루는 범위
  • 실행 가능성 (20%): 가이드를 따라 실제 배포할 수 있는 수준의 구체성
예상 결과에어갭 시 할루시네이션(존재하지 않는 옵션/명령어 생성) 위험 높음. 화이트리스트로 공식 문서 접근 시 정확성·최신성 대폭 향상. 이 시나리오에서 인터넷 접근의 가치가 가장 명확하게 드러날 것

시나리오 S5: 주어진 자료 기반 분석 — 순수 모델 능력 비교

사내 LLM SotA 모델 에어갭
테스트 목적인터넷 접근 변수를 제거하고, 주어진 자료만으로 분석·작성하는 능력을 순수 비교. 에어갭 환경에서의 현실적 사용 시나리오
입력 조건 프롬프트: "아래 제공된 보안 감사 보고서 원문, 네트워크 토폴로지 문서, 취약점 스캔 결과를 분석하여 경영진용 보안 현황 요약 보고서를 작성하라. 주요 발견사항, 위험도 매트릭스, 권고 조치 우선순위를 포함."
참고자료: 3개 문서 제공 (총 약 5,000 단어). 모든 정보가 입력에 포함됨
인터넷: 완전 차단 (이 시나리오에서는 인터넷 불필요)
평가 기준
  • 분석 깊이 (30%): 단순 요약이 아닌 교차 분석, 패턴 발견, 인사이트 도출
  • 정확성 (25%): 원문 정보와의 일치도, 수치/사실관계 정확성
  • 구조화 (20%): 경영진 대상 보고서로서의 구조, 우선순위 매트릭스 적절성
  • 실행 가능한 권고 (25%): 구체적이고 현실적인 대응 방안 제시 여부
예상 결과이 시나리오는 인터넷 무관하므로 순수 LLM 능력 비교. SotA가 분석 깊이, 교차 분석, 경영진용 톤 조절에서 우위 예상. 그러나 다른 시나리오 대비 격차가 가장 작을 수 있음 (모든 정보가 주어졌으므로)

시나리오 S6: 코드 리뷰/분석 — 에어갭 실전 시나리오

사내 LLM SotA 모델 에어갭
테스트 목적에어갭 환경에서 가장 빈번하게 사용될 코드 리뷰 시나리오의 품질 비교. 보안 취약점, 성능 이슈, 코드 스멜 탐지 능력 평가
입력 조건 프롬프트: "아래 Python 웹 애플리케이션 코드를 리뷰하라. 보안 취약점, 성능 병목, 코드 스멜, 테스트 누락 영역을 식별하고 구체적인 수정 방안을 제시하라."
참고자료: 의도적으로 10개의 이슈(SQL injection 2건, XSS 1건, N+1 쿼리 2건, 미흡한 에러 처리 3건, 하드코딩된 시크릿 1건, 레이스 컨디션 1건)를 심어둔 테스트 코드 (약 500 LoC)
인터넷: 완전 차단
평가 기준
  • 탐지율 (40%): 심어둔 10개 이슈 중 몇 개를 발견했는가 (Recall)
  • 정밀도 (20%): 보고한 이슈 중 실제 이슈인 비율 (Precision). 허위 양성(false positive) 비율
  • 수정안 품질 (25%): 제안된 수정 코드의 정확성과 완성도
  • 우선순위 적절성 (15%): 보안 > 성능 > 스멜 순서로 적절히 우선순위 부여하는지
예상 결과SotA 모델이 탐지율에서 우위 (8-10개 vs 5-7개 예상). 특히 레이스 컨디션, N+1 쿼리 같은 맥락 의존적 이슈에서 격차가 클 것. 단순 패턴 매칭(하드코딩 시크릿, SQL injection)은 양쪽 모두 탐지 가능

시나리오 S7: 하네스 엔지니어링 효과 — 동일 모델, 다른 하네스

사내 LLM 에어갭 하네스 비교
테스트 목적동일한 사내 LLM을 사용하되, 하네스(에이전트 루프, 시스템 프롬프트, 도구)를 달리했을 때 품질 차이 측정. 하네스 엔지니어링 투자 가치 판단
입력 조건 동일 프롬프트를 3가지 방식으로 실행:
(a) 단순 API 호출: 시스템 프롬프트 최소, 도구 없이 단일 턴 요청
(b) 기본 에이전트: Crush 기본 설정. 파일 읽기/쓰기/터미널 도구 활성화
(c) 강화된 에이전트: 커스텀 시스템 프롬프트 + 자기 검증 루프 + 문서 템플릿 도구 추가
프롬프트: S3과 동일 (코드베이스 기반 SDD 작성)
평가 기준S3과 동일한 평가 기준 사용. 모델은 동일하므로 하네스의 순수 기여도를 측정
예상 결과(a) → (b) → (c)로 갈수록 품질 향상 예상. 특히 (c)에서 자기 검증 루프가 완성도를 높이고, 템플릿 도구가 구조적 완성도를 향상시킬 것. 이 격차가 하네스 투자의 ROI 근거

3-2. 기능 비교

Cowork 전용 기능

  • VM 격리 실행: macOS Virtualization.framework 기반 Ubuntu VM. 세션마다 임시 디스크, 랜덤 사용자
  • 3중 네트워크 방어: gVisor(시스콜 차단) + MITM 프록시(TLS 검사) + 도메인 화이트리스트
  • 50+ 관리형 커넥터: Slack, Notion, Google Drive, Asana, Linear, Jira, GitHub 등 원클릭 연동
  • Computer Use 기본 탑재: 호스트 Chrome을 MCP로 제어. 실제 로그인 세션으로 웹 탐색
  • Dispatch (전화 제어): 원격으로 전화 자동 응답/발신 (실험적 기능)
  • "디지털 동료" UX: 장기 실행 작업, 프로젝트 컨텍스트 유지, 비개발자 대상 인터페이스

Claude Code 전용 기능

  • 로컬 셸 직접 접근: 호스트 터미널에서 모든 명령어 직접 실행. 개발 환경 완전 접근
  • IDE 통합: VS Code, JetBrains IDE 확장으로 에디터 내 직접 사용
  • Agent Teams: 여러 에이전트가 피어 투 피어로 병렬 작업. 독립된 Git 워크트리에서 작업
  • Git 워크트리 격리: 에이전트가 별도 브랜치에서 작업, 메인 브랜치 영향 없음
  • --remote / Teleport: CLI 세션을 웹으로 이동하여 원격에서 계속 작업
  • Hooks 시스템: 도구 호출 전후에 커스텀 셸 스크립트 실행 (CI/CD 통합)

3-3. 하네스 엔지니어링 분석

"Cowork 수준의 품질"을 재현하려면 LLM만이 아니라 하네스 엔지니어링의 세 가지 층을 이해해야 한다.

Layer 1: 시스템 프롬프트

  • 110개 이상의 조건부 문자열로 구성. 사용 모드(Code/Cowork), 도구 상태, 작업 유형에 따라 동적으로 조합
  • Cowork 모드에서는 "디지털 동료" 포지셔닝, 문서 작성 가이드라인, 사용자 선호 스타일 추적 등이 추가
  • 재현 난이도: 매우 높음 — 수만 줄의 프롬프트 엔지니어링은 코드 복제로 되지 않음. 수개월의 반복 실험과 평가 결과물

Layer 2: 에이전트 루프 + 도구 오케스트레이션

  • Plan → Execute → Verify 반복 루프. 작업 분해, 서브에이전트 위임, 자기 검증
  • 30+ 빌트인 도구의 인터페이스 설계가 LLM의 정확한 도구 사용을 유도
  • 도구 결과의 컨텍스트 관리: 1M 토큰 윈도우의 효율적 활용, 필요 시 압축/요약
  • 재현 난이도: 높음 — 에이전트 루프 자체는 오픈소스 구현 다수 존재. 그러나 도구 인터페이스의 세밀한 설계(에러 메시지 형식, 결과 포맷 등)가 품질에 영향

Layer 3: Skills (전문 도구)

  • 작업 유형별 전문화된 지시와 도구 세트를 필요 시점에만 로드 (Progressive Disclosure)
  • docx, pptx, xlsx 등 바이너리 포맷 처리를 도구가 캡슐화하여 LLM이 콘텐츠에 집중
  • 재현 난이도: 중간 — Skills의 도구 부분은 오픈소스 라이브러리(docx, PptxGenJS, openpyxl)로 구현 가능. 프롬프트 부분이 품질 차이를 만드는 핵심
핵심 인사이트: 하네스의 3개 층 중 Layer 1(시스템 프롬프트)이 품질 차이의 가장 큰 원인이다. 코드는 복제할 수 있지만, 시스템 프롬프트는 수천 시간의 A/B 테스트와 사용자 피드백의 결정체이며 특정 LLM(Claude)에 최적화되어 있다. 다른 LLM에서는 동일한 시스템 프롬프트라도 다르게 동작한다.

3-4. 문서 생성 워크플로우 (Cowork)

Cowork의 문서 생성은 Unpack → Edit → Repack 패턴으로 작동한다.

입력 문서 (docx)
→
Unpack (ZIP 해제)
→
LLM 분석 (XML 파싱)
→
Edit (XML 수정)
→
Repack (ZIP 재조립)
→
결과 문서 (docx)

단계별 상세

단계 수행 주체 상세 동작
1. Unpack 도구 (Skills) docx 파일을 ZIP으로 해제 → 내부 XML 파일들(document.xml, styles.xml 등) 추출. LLM이 텍스트로 읽을 수 있는 상태로 변환
2. 분석 LLM XML 구조를 파싱하여 문서 구조, 스타일, 콘텐츠를 이해. 수정/생성할 내용을 결정 (의미적 판단)
3. Edit LLM + 도구 LLM이 Edit 도구로 XML 문자열을 직접 치환하거나, Python 스크립트(openpyxl, python-docx)를 작성하여 도구가 실행. 새 문서 생성 시 JavaScript docx 라이브러리로 프로그래밍 생성
4. 검증 도구 (Skills) 자동 수리: invalid durableId 복구, xml:space 속성 보정, 스키마 준수 검증. Smart quote 보존, tracked changes 유지
5. Repack 도구 (Skills) 수정된 XML들을 다시 ZIP으로 조립하여 유효한 docx 파일 생성
LLM과 도구의 역할 분담이 핵심:
• LLM 담당: "무엇을 쓸 것인가" (콘텐츠 결정, 구조 설계, 톤 조절) — 의미적 판단
• 도구 담당: "어떻게 포맷팅할 것인가" (XML 조작, ZIP 처리, 스키마 준수) — 기술적 처리
• 이 분리 덕분에 LLM은 "Word 파일 형식을 알 필요 없이" 콘텐츠에만 집중할 수 있다.
• Word의 내부가 XML이라는 사실이 이 패턴을 가능하게 한다 — LLM은 XML을 잘 처리한다.

3-5. 시사점: 재현 가능성 분석

사내 플랫폼 구축 관점에서, Cowork의 각 구성 요소별 재현 가능성을 평가한다.

구성 요소 재현 가능성 근거 필요 조건
에이전트 루프 가능 Crush, Aider 등 오픈소스에 이미 구현. Plan-Execute-Verify 패턴은 표준화됨 기존 도구 활용 또는 Agent SDK 기반 자체 구현
빌트인 도구 가능 Read, Edit, Write, Bash, Grep 등 파일/터미널 조작 도구는 범용적 기존 도구(Crush)에 대부분 내장
VM 격리 + 네트워크 제어 가능 K3s Pod 격리 + NetworkPolicy + 이그레스 프록시로 동일 패턴 구현 가능 프록시 인프라 구축 (안 B 아키텍처)
문서 Skills (도구 부분) 부분 가능 docx/pptx/xlsx 처리는 오픈소스 라이브러리(docx, openpyxl 등)로 가능. Unpack-Edit-Repack 패턴 구현 가능 Skills 개발 공수 (2-4주 예상). 자동 수리/검증 로직이 관건
시스템 프롬프트 어려움 110+ 조건부 문자열은 수천 시간의 실험 결과물. Claude에 최적화되어 있어 다른 LLM에서는 다르게 동작 자체 LLM에 맞는 시스템 프롬프트를 처음부터 개발·최적화 필요. 장기 투자
LLM 품질 (Claude Opus) 불가 Qwen 3.5 등 사내 모델로는 Claude Opus의 추론·문서 작성 능력 재현 불가능. 모델 크기와 학습 데이터의 근본적 차이 더 큰/좋은 사내 모델 도입, 또는 특정 도메인 파인튜닝으로 격차 축소. 완전 해소는 현실적으로 어려움
관리형 커넥터 (50+) 어려움 Slack, Notion 등 50+ 서비스 커넥터를 자체 구축·유지하는 것은 비현실적 사내 필수 서비스(GitLab, Jira 등)만 선별적으로 MCP 서버 구축
Computer Use 어려움 스크린샷 인식 + 클릭/타이핑 자동화는 멀티모달 LLM 능력에 의존. 사내 LLM의 비전 능력이 부족할 가능성 멀티모달 지원 사내 LLM 필요. PoC 범위 밖 권장
클린룸 재구현에 대한 현실적 평가:

팀장이 제안한 "유출 코드 기반 클린룸 재구현"의 핵심 난제는 코드 구조가 아니다.

1. 시스템 프롬프트는 코드가 아니라 노하우다.
   46K LoC의 QueryEngine.ts 중 상당 부분이 조건부 프롬프트 조합 로직. 이것을 복제하더라도 사내 LLM(Qwen 등)에서는 Claude와 다르게 반응한다. 모든 프롬프트를 사내 LLM에 맞게 재튜닝해야 한다.

2. 품질 = LLM × 하네스의 곱이다.
   하네스를 완벽히 재현해도 LLM 성능이 70%이면 최종 품질은 70% 수준. "Cowork 수준 품질"이란 Claude Opus + 최적화된 하네스의 결과물이므로, 사내 LLM으로는 구조적으로 동일 품질 달성이 어렵다.

3. 현실적 대안:
   클린룸 대신, 기존 오픈소스 에이전트(Crush 등)를 기반으로 사내 LLM에 최적화된 시스템 프롬프트와 문서 Skills를 점진적으로 개발하는 것이 투자 대비 효과가 높다.

권장 구현 우선순위

우선순위 구성 요소 접근 방법 기대 효과
P0 에이전트 루프 + 빌트인 도구 기존 Crush 활용 (이미 완료) 기본 코딩 어시스턴트 기능 즉시 사용 가능
P1 사내 LLM 최적화 시스템 프롬프트 Qwen/DeepSeek에 맞는 프롬프트 개발·평가 반복 동일 모델에서 20-40% 품질 향상 기대 (S7 시나리오로 검증)

P4 사내 LLM 업그레이드 더 큰 모델 도입 또는 코딩/문서 특화 파인튜닝 근본적 품질 향상. 가장 큰 효과이나 가장 큰 투자
